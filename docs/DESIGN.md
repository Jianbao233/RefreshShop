# RefreshShop 技术结构

对应 0.3.0。

## 配置

`RefreshShopConfig` 持有运行值与迁移标记，`SettingsStore` 负责 JSON 读写，`ModConfigSettingsAdapter` 与 `RitsuLibSettingsProvider` 连接可选设置框架。

启动先读本 Mod JSON。ModConfig 注册并载入旧文件后，只导入缺失的键；缺失键不会提前用默认值写满。RitsuLib 和 ModConfig 的主动修改都立即保存。注册及镜像回调受保护，避免旧值覆盖新值或递归保存。写入完整临时文件后替换目标，成功内容不重复写入。

## 刷新事务

`GameApi` 集中解析游戏 API，按精确参数或唯一可赋值签名调用，不按参数数量猜测。生产 DLL 不绑定具体 `sts2.dll`；原生测试则直接引用选定 SDK。

`ShopRefreshService.RefreshAsync` 的步骤：

1. 检查本地玩家、连接、余额、剩余次数和同步／扣费接口，阻止重入。
2. `RefreshPlan` 克隆条目形成临时库存，生成全部候选与价格。
3. 将结果应用到原条目，保留原对象、事件与 UI 绑定；等待原生 `LoseGold` 完成并核对金额。
4. 提交独立随机状态和一次使用次数，发送一次原生 `SyncLocalGoldLost`。

生成失败不触碰真实条目；扣费失败恢复条目、金币及消费记录，并移除本次临时造出的卡。发送异常发生在提交之后，不能证明消息未发出：保留已提交结果，并停止本商店后续刷新，避免退款或重试导致进一步分歧。

每份库存用 `ConditionalWeakTable` 保存重入标记、刷新随机状态、同步异常标记和次数。关闭再打开同一份商店 UI 不会刷新额度。该状态不进入游戏存档。

## 商品与随机数

- 卡牌使用原生 `Populate`，保留类型、稀有度、升级、折扣和卡牌生成钩子。先过滤黑名单，并检查生成钩子的最终结果。
- 遗物从角色与共享解锁池取合法候选，检查 `IsAllowedInShops` 与当前运行的 `IsAllowed`，排除已持有及本次重复遗物。第三槽保留 `Shop` 稀有度，不消耗原生遗物抓取袋。
- 药水从原生角色／共享合法池产生，保留 10% 稀有、25% 罕见、65% 普通分布。过滤导致某稀有度为空时使用其他合法候选；全空时拒绝刷新。
- 商品价格由原生条目的 `CalcCost` 计算。删卡服务不刷新；已购买的空槽是否补回由设置决定。

生成前暂时加载本地刷新随机状态，生成后在 `finally` 恢复完整 `PlayerRngSet`。只有成功提交才推进下一次刷新状态，避免单装玩家推进其他端的原生随机流。此范围不包含第三方钩子额外修改的任意全局状态。

## UI 与加载

游戏的 ModManager fallback loader 负责一次 `PatchAll`；延迟初始化只注册设置，不能再次安装补丁。

`NMerchantInventory.Initialize` 后注入原生 `pause_menu_button.tscn`，与删卡服务位于同一动画容器，避免挡住删卡点击区。文字由金币、次数、配置和容器变化事件更新。购买后重新连接原生焦点导航；原生输入锁也控制刷新按钮。退出 UI 树时解除所有订阅。

## 单装网络边界

`affects_gameplay=false` 使 RefreshShop 出现在原生握手的非强制一致 Mod 列表；它在游戏内容上确实会改变商店选择，因此这个标记的用途是兼容握手，不是宣称无玩法影响。

库存刷新是本地操作；金币及购买仍由原生 `RewardSynchronizer` 处理。没有新增消息类型、模型 ID 或对方必需执行的 Mod 逻辑。对方不能拥有未知的自定义商品，本 Mod 也不解决其他 Mod 的互斥或内容差异。

测试分三层：配置跨进程测试；原生模型／消息序列化／按钮场景回归；两个独立进程的原生 ENet 握手与收发。最后一层只在安装端动态加载 Mod，另一个进程逐步确认它从未加载该程序集。进程间文件只传测试就绪信号和预期结果，游戏变化必须经 ENet 与原生接收器才能通过断言。

完整 Steam 邀请、远程网络、两端可见游戏界面及后续战斗是独立的验收范围，不能由无头测试替代。
